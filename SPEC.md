# SPEC: To do list с AI-приоритезацией задач

**Статус:** реализовано · **Дата:** 22.10.2026 · **Сайт:** https://todo-list-ai-three.vercel.app

## 1. Цель

Веб-приложение для ведения списка дел, которое умеет с помощью AI расставлять приоритеты задачам и объяснять, почему задача важна.

AI-функции подключаются через API-ключ. **Ключа пока нет**, поэтому:
- приложение полностью работает без ключа как обычный список дел;
- вся инфраструктура для ключа (конфигурация, проверка, интерфейс, обработка ошибок) реализуется сразу;
- чтобы включить AI, достаточно добавить ключ, код менять не нужно.

## 2. Область работ

### Входит в MVP
- CRUD задач: создание, редактирование, удаление, отметка о выполнении.
- Поля задачи: название, описание, срок, ручной приоритет.
- Фильтры (все / активные / выполненные) и сортировка (по приоритету, сроку, дате создания).
- Хранение задач локально, без аккаунта.
- Аккаунты по email и паролю, синхронизация задач между устройствами (Vercel + Neon, как в NutriLens).
- Слой AI-провайдера с поддержкой API-ключа и режимом «ключ не задан».
- Кнопка «Расставить приоритеты с AI» и объяснение приоритета у каждой задачи.

### Не входит в MVP
- Подтверждение email и восстановление пароля по почте.
- Напоминания и уведомления.
- Совместная работа.

## 3. Пользовательские сценарии

| # | Сценарий | Ожидаемый результат |
|---|----------|---------------------|
| 1 | Пользователь добавляет задачи без ключа | Всё работает, AI-кнопка неактивна и подсказывает: «Добавьте API-ключ, чтобы включить AI» |
| 2 | Администратор добавляет ключ в `.env` и перезапускает сервер | AI-кнопка становится активной |
| 3 | Пользователь нажимает «Расставить приоритеты с AI» | Активные задачи получают приоритет и короткое обоснование, список пересортировывается |
| 4 | Пользователь не согласен с AI | Меняет приоритет вручную, ручное значение помечается и AI его не перезаписывает |
| 5 | Ключ неверный или лимит исчерпан | Понятное сообщение об ошибке, задачи не меняются |
| 6 | Гость регистрируется по email | Аккаунт создан, задачи из браузера переносятся в аккаунт |
| 7 | Пользователь входит на другом устройстве | Задачи загружаются с сервера; локальные задачи объединяются с серверными |
| 8 | Задачи изменены на двух устройствах одновременно | Правки объединяются: по каждой задаче побеждает более свежая, удаление не «воскресает» |
| 9 | Пользователь выходит из аккаунта | Задачи удаляются с этого устройства и остаются в аккаунте |

## 4. Модель данных

```ts
type Priority = 'critical' | 'high' | 'medium' | 'low';

interface Task {
  id: string;
  title: string;            // обязательно, 1–200 символов
  description?: string;     // до 2000 символов
  dueDate?: string;         // ISO 8601, дата
  done: boolean;
  priority: Priority;       // по умолчанию 'medium'
  prioritySource: 'manual' | 'ai' | 'default';
  aiReason?: string;        // объяснение от AI, до 200 символов
  aiScore?: number;         // 0–100, для сортировки внутри одного приоритета
  createdAt: string;        // ISO 8601
  updatedAt: string;
}
```

## 5. Архитектура

```
Браузер (HTML/CSS/JS)  ──►  Функции Vercel (api/, Node.js 22)  ──►  AI-провайдер (Anthropic Claude)
   UI, localStorage          аккаунты, сессии, синхронизация,   ──►  Neon Postgres (users, sessions,
   cloud.js (синхронизация)  прокси к AI, хранит API-ключ             user_data)
```

Локально те же функции запускает `scripts/dev.mjs` (`npm run dev`). Без `DATABASE_URL` аккаунты выключены и приложение работает только с `localStorage`.

**Почему через сервер:** API-ключ не должен попадать в браузер. Фронтенд никогда не видит ключ и обращается только к своему серверу.

## 6. Работа с API-ключом

### 6.1 Конфигурация
`.env.example`:
```dotenv
# AI-провайдер: anthropic | mock | none
AI_PROVIDER=anthropic

# API-ключ. Пусто = AI выключен, приложение работает без него.
ANTHROPIC_API_KEY=

# Модель (необязательно)
AI_MODEL=claude-opus-5-5

# Таймаут запроса к AI, мс
AI_TIMEOUT_MS=30000

# Порт сервера
PORT=3000
```

### 6.2 Правила
- Ключ читается только на сервере из переменной окружения `ANTHROPIC_API_KEY`: локально из `.env`, на Vercel из переменных проекта.
- Ключ не логируется, не отдаётся клиенту и не попадает в сообщения об ошибках.
- При старте сервер определяет режим:
  - ключ пустой или `AI_PROVIDER=none` → провайдер `disabled`, в лог пишется `AI: выключен (ключ не задан)`;
  - ключ задан → провайдер `anthropic`, в лог пишется `AI: включён (модель …)`.
- Формат ключа проверяется только поверхностно (непустая строка). Настоящая проверка — первый запрос к API.
- `.env` добавлен в `.gitignore` с первого коммита.

### 6.3 Интерфейс провайдера
```ts
interface AIProvider {
  readonly enabled: boolean;
  prioritize(tasks: TaskInput[], context: { today: string }): Promise<PriorityResult[]>;
}

interface TaskInput { id: string; title: string; description?: string; dueDate?: string; }
interface PriorityResult { id: string; priority: Priority; score: number; reason: string; }
```
`disabled.js` возвращает `enabled: false`, а его `prioritize` выбрасывает ошибку `AI_DISABLED`. Новый провайдер добавляется отдельным файлом без изменений в UI.

## 7. API сервера

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/api/ai/status` | `{ enabled, provider, model?, requiresAuth }` — ключ не возвращается |
| `POST` | `/api/ai/prioritize` | Тело: `{ tasks: TaskInput[] }`, ответ: `{ results: PriorityResult[] }`. При включённых аккаунтах — только после входа |
| `POST` | `/api/auth/register` | Регистрация по email и паролю и сразу вход |
| `POST` | `/api/auth/login` | Вход |
| `POST` | `/api/auth/logout` | Выход |
| `GET` | `/api/auth/me` | Кто вошёл |
| `POST` | `/api/auth/password` | Смена пароля, остальные устройства выходят |
| `GET` / `PUT` | `/api/data` | Загрузить / сохранить задачи `{ tasks, deleted }` с номером версии; при устаревшей версии — `409` с серверной копией |
| `DELETE` | `/api/account` | Удалить аккаунт и все задачи (нужен пароль) |

Ошибки возвращаются в формате RFC 9457: `{ code, detail }`, где `detail` — текст для пользователя на русском. Изменяющие запросы принимаются только со своего сайта (заголовок `x-td: 1` и проверка `Origin`).

### Ошибки `/api/ai/prioritize`
| Код | `code` | Когда | Сообщение в UI |
|-----|---------|-------|----------------|
| 503 | `AI_DISABLED` | Ключ не задан | «AI выключен: на сервере не задан API-ключ» |
| 401 | `UNAUTHORIZED` | Аккаунты включены, а пользователь не вошёл | «Войдите в аккаунт, чтобы использовать AI» |
| 401 | `AI_AUTH` | Провайдер отклонил ключ | «API-ключ недействителен» |
| 429 | `AI_RATE_LIMIT` | Превышен лимит | «Слишком много запросов, попробуйте позже» |
| 502 | `AI_BAD_RESPONSE` | Ответ не прошёл валидацию | «AI вернул некорректный ответ» |
| 504 | `AI_TIMEOUT` | Провайдер не ответил вовремя | «AI не ответил вовремя, попробуйте ещё раз» |
| 400 | `BAD_REQUEST` | Пустой список или больше 50 задач | «Нет задач для приоритезации» |

### 7.1 Аккаунты и безопасность
- Регистрация по email и паролю, пароль не короче 10 символов, не совпадает с email и не из списка простых.
- Пароли — `scrypt` со случайной солью. Сессия — случайный токен в cookie `td_session` (`HttpOnly; Secure; SameSite=Lax`, 30 дней), в базе хранится только его SHA-256.
- После 5 неверных паролей вход блокируется на 15 минут; время ответа для несуществующего email такое же.
- AI на сервере с аккаунтами доступен только вошедшим пользователям, чтобы ключ не расходовался анонимно.

### 7.2 Синхронизация
- Задачи живут в `localStorage`; при входе копия хранится в `user_data.data` (`jsonb`) с номером версии.
- Правки отправляются через ~1 секунду. Если версия на сервере новее (`409`), клиент объединяет данные и отправляет снова.
- Объединение: по каждой задаче побеждает более свежий `updatedAt`; удалённые задачи хранятся в `deleted` (id → время, 30 дней) и не «воскресают».
- Без связи изменения копятся локально и отправляются при появлении сети.

## 8. Логика AI-приоритезации

### 8.1 Что отправляется
Только активные задачи (`done: false`), у которых `prioritySource !== 'manual'`. Максимум 50 за один запрос. Отправляются только `id`, `title`, `description`, `dueDate` и текущая дата.

### 8.2 Критерии для модели
1. Срочность: просрочено или срок сегодня/завтра → выше.
2. Важность и последствия невыполнения, судя по тексту задачи.
3. Блокирующие задачи (от них зависят другие) → выше.
4. Короткие задачи с высокой ценностью → выше внутри своего уровня.

### 8.3 Формат ответа
Модель возвращает строго JSON (через structured output / tool use):
```json
{ "results": [ { "id": "abc", "priority": "high", "score": 82, "reason": "Срок завтра, блокирует отчёт" } ] }
```
Сервер проверяет: каждый `id` есть во входных данных, `priority` из допустимого списка, `score` от 0 до 100, `reason` не длиннее 200 символов. Невалидные элементы отбрасываются, если невалидно всё — ошибка `AI_BAD_RESPONSE`.

### 8.4 Применение результата
- Задачи получают `priority`, `aiScore`, `aiReason`, `prioritySource: 'ai'`.
- Задачи с ручным приоритетом не меняются.
- Перед применением сохраняется снимок, доступна кнопка «Отменить» (10 секунд).

## 9. Интерфейс

- **Индикатор AI** в шапке: «AI: выключен» (серый) / «AI: включён» (зелёный) по данным `/api/ai/status`.
- **Кнопка «Расставить приоритеты с AI»:**
  - без ключа неактивна, подсказка объясняет, как включить;
  - во время запроса — спиннер, кнопка заблокирована;
  - после ответа — тост «Обновлено N задач» и «Отменить».
- **Карточка задачи:** цветная метка приоритета, иконка ✨ у AI-приоритета, объяснение по наведению или нажатию.
- **Ручной приоритет:** выпадающий список, после выбора у задачи появляется значок 🔒 «закреплено вручную».

## 10. Нефункциональные требования
- Без ключа приложение не делает внешних запросов.
- Таймаут AI-запроса настраивается (`AI_TIMEOUT_MS`, по умолчанию 30 секунд), по истечении — понятная ошибка.
- Адаптивная вёрстка от 360 px, светлая и тёмная тема.
- Без аккаунта задачи хранятся только в `localStorage` и уходят на сервер только при нажатии AI-кнопки. С аккаунтом — синхронизируются с базой.
